## Recommendation in ten lines

1. Build three small parts: an **area tree** (pure C++, a split tree whose leaves are areas), a **view registry** (view type id to QML component, minimum size, multiplicity, what it needs), and a **workspace store** (named trees, one file in the root's state folder). The QML is a recursive `AreaNode` that draws a split or a leaf.
2. Write our own splitter (ratios kept in the tree, proportional on window resize), not `SplitView`: its sizes are pixels and its saved state is an opaque byte array.
3. A leaf is `{area id, view type, view state}`. The view state is the per-area state (camera, tool, pin, follow); the data stays shared, as in Blender, where areas keep their own editor data and look at the same document.
4. Each view gets one small `ViewContext` object: its area id, its persisted state, `follow` (selection or a pin), and the `ActiveTarget` the app derives from the Graph selection (node id, kind, canvas id, region). Everything else stays on the `App` singleton: project, workflows, runs, run queue, theme, commands.
5. Views follow the active target unless pinned (Blender's Image Pin and Properties pin; ComfyUI's right panel follows the canvas selection). Selecting a Paint node moves a Mask view to it; selecting a Canvas Region moves the Canvas view to its canvas and frames its rectangle.
6. Keys: the active area (click or keyboard focus, drawn with an accent outline) owns the view's key contexts; wheel and hover act under the pointer. The global command registry stays; `canvas` and the other contexts switch on while a view of that type is active.
7. Undo is scoped to the active area's view: the Graph's per-tab `QUndoStack`; a Mask or Paint view keeps its layer undo and commits one graph step; the Canvas view uses revisions.
8. Modal editors become views by splitting the frame from the content: `LargeViewDialog` stays as a thin wrapper around the same content item; MaskEditor, CanvasHistory, RunQueuePanel and the Results browser are already close to "content with a property set".
9. Slice 0 changes nothing visible: one area, the Graph view exactly as today (same item, same `objectName`, no extra items), a registry with one type, an empty store; the layout file is only written once the user changes the layout.
10. Order: 0 container; 1 split, resize, header with the type menu, Queue and Results views; 2 shared active target, follow and pin, History and Viewer; 3 Mask and Paint views; 4 workspaces as tabs and presets; 5 Canvas view (build #216's content as a view-ready item from the start); 6 Properties; 7 drag, swap, maximize, new window.

# 2. Prior art

## 2.1 Blender (areas, editors, workspaces)

Sources, all verified by fetching the pages on 2026-11-22: the Blender manual (https://docs.blender.org/manual/en/latest/): `interface/window_system/areas.html`, `regions.html`, `workspaces.html`, `editors/image/introduction.html`, `compositing/types/output/viewer.html`, `editors/properties_editor.html`, `editors/preferences/interface.html`; and the developer page https://developer.blender.org/docs/features/interface/editors/. Manual text is CC-BY-SA; the code is GPL and was not read.

**Screen, area, region.** The window is divided into rectangles called areas; an area reserves space for an editor; areas are grouped into workspaces (areas page). Every editor is divided into regions: a header (menus and common tools, top or bottom), the main region (at least one region is always visible), a toolbar, a sidebar (N), tool settings, a footer, an "adjust last operation" panel (regions page). Regions hide by dragging them to nothing and leave a small arrow to bring them back. The header context menu offers Show Header, Flip to Bottom/Top, split, maximize, duplicate into new window, close area.

**Data model (developer page).** An editor is a `ScrArea` in the `areabase` list of a screen, which is in a window. Each editor type keeps its own data in a struct that derives from `SpaceLink`; the area holds a *list* of these (`spacedata`), the first being the active editor, "so that it can contain the data of every editor that has occupied the same space, allowing quick switching between them". A `SpaceType` holds the callbacks (create, free, activate, refresh, save), the name, icons and keymaps. So: **switching an area's editor type keeps the old type's state in the area**, and the type's state is separate from the document. Fugue should copy this: the area keeps a map `viewType -> state`, so switching Graph to Results and back keeps the camera.

**Editor type menu.** The editor-type dropdown sits in the header. The manual groups the types as 3D, image, UV, compositor, node editors, video, animation, scripting, data (outliner, properties, file browser, asset browser, spreadsheet, preferences).

**Resize, split, join, swap.** Drag a border to resize (Ctrl snaps, Shift moves aligned borders together). Docking works from an area corner: drag inward to split (left/right gives a vertical split, up/down a horizontal one) or into a neighbour to join it; drag into the middle of another area to replace it; Ctrl+corner drag swaps the contents of two areas in the same window; right click on a border opens Vertical/Horizontal Split, Join, Swap Areas. Esc or right click cancels the drag. A Ctrl+Space "Toggle Maximize Area" keeps the editor's header and status bar and restores the layout; Ctrl+Alt+Space Focus Mode hides the top bar, status bar and the editor's own secondary regions. "Duplicate Area into New Window" makes a floating, fully working copy in the same instance (multi-monitor). Fugue already has a focus mode (`H`, #129) that behaves like Blender's Focus Mode for chrome.

**Keys follow the hover.** The manual says that while some shortcuts are global, "many depend on which editor the mouse cursor is hovering over" (its example: Ctrl-J in the Outliner does nothing; the shortcut belongs to the 3D Viewport).

**Workspaces.** "Workspaces are essentially predefined window layouts": a set of areas containing editors for a task. Tabs in the top bar switch; double click renames; add from a template (Modeling, Sculpting, Compositing, ...); duplicate copies "the screen layout and editors"; delete (not the last); reorder; Ctrl+PageUp/PageDown. Workspaces are saved in the blend file; opening a file with *Load UI* uses the file's layout instead of the current one; a custom set can be saved as the Defaults (startup file). Per-workspace settings: *Pin Scene* (the workspace remembers the scene), *Mode* (switched on activation), add-on filter. A workspace is not a document: switching it changes the layout and a few modes, never the data.

**User preferences for layout.** Preferences > Interface > Editors: Region Overlap, Corner Handles ("small handles in the corners of each area ... to split or join ... especially useful on touch-enabled devices"), Border Width (the hit zone of area controls, for pen, touch and accessibility), Header Position (keep existing, top, bottom), and **Temporary Editors**: what happens when an operation needs an editor (render result: maximize area, replace the largest image editor, or a new window; file browser; preferences: maximize area or new window). Fugue lesson: modal dialogs that become views need a rule for "open this in a view": reuse a matching area, else replace the largest, else a temporary overlay. Blender's rule is a user preference.

**One editor in two areas.** Areas are independent: two 3D viewports show one scene with separate cameras, because the camera is region/space state and the scene is shared data. [U] The manual pages read here do not state this in a sentence; it is the standard behaviour and follows from the `SpaceLink` design above. Selection is data (in the scene), so it is shared across areas; view state is per area.

**Image Editor and Node Editor (the interaction to copy).** The Image Editor "lets you create, view, and edit images, as well as see render results and intermediate Compositor output". It has a mode (View, Paint, Mask) in its header, so paint and mask editing are modes of the image editor, not separate editors. Its data-block selector lists images, the **Render Result** and the **Viewer Node** ("displays the image that's fed into the Viewer Node in the Compositor"). The Viewer node "previews image data ... at any point within a compositor node tree", is connected by Shift-Ctrl-LMB on a node, and the active viewer node is the one marked in its header; selecting another viewer node switches. With Backdrop on, the same image is drawn behind the node tree, and "Active Node" gizmos in the Image Editor let a property of the active compositing node be adjusted directly in the image (Viewer node image only). Follow with a pin: **Image Pin** "prevents the Image Editor from automatically switching to the texture of the selected object" (it follows in Texture Paint mode otherwise); the Properties editor's **Toggle Pin ID** "locks the editor to the current data-block, preventing it from changing when the selection updates", unpinning "returns to context-based display". So Blender's answer to "select a node and another editor follows" is: the editor follows the active context by default, an explicit pin freezes it, and the follow rule can depend on the editor's mode.

**Temporary window for heavy editors.** Preferences and a render result open as a temporary maximized area or window. Fugue's Settings stays a dialog for now.

## 2.2 Other applications

- **VS Code (MIT, source read).** `src/vs/base/browser/ui/grid/gridview.ts` is the model to copy in shape: a `GridView` is a tree of split views whose levels alternate orientation, a `BranchNode` (children, orientation, size) and a `LeafNode` (a view). A view declares `minimumWidth/maximumWidth/minimumHeight/maximumHeight` and `layout(width, height, top, left)`; a branch's minimum is the largest minimum of its visible children. `proportionalLayout` (default true) resizes views proportionally. Serialization is `ISerializedGridView {root, orientation, width, height}` with `ISerializedNode` either `{type:'leaf', data, size, visible?, maximized?}` or `{type:'branch', data:[...], size, visible?}`; `deserialize` validates numbers and requires the root to be a branch. The workbench has fixed containers (activity bar, primary and secondary side bar, editor area with editor groups, panel, status bar); a *view container* hosts views (tree view, webview) that "can be moved between areas" (https://code.visualstudio.com/api/ux-guidelines/overview). Takeaways: leaves carry opaque serialized data; sizes are stored as proportions; min sizes come from the view; maximizing a leaf is a flag in the tree. Fugue wants Blender's free area types, not VS Code's fixed zones.
- **Krita (GPL; manual only).** Dockers are panels; a *workspace* is a "saved configuration of dockers" recording grouping and place; reachable from the toolbar or Window > Workspaces; import from a `.kws` file; a separate "window layouts" feature stores several windows and their monitors; *sessions* store open images and windows, separate from workspaces (https://docs.krita.org/en/reference_manual/resource_management/resource_workspace.html). Takeaway: layout, window set and open documents are three separate things. Fugue already has tabs (#212) as the third; keep them apart.
- **Photoshop (docs via search snippets; the pages answered 403 earlier [U], re-read only as snippets).** Window > Workspace > New Workspace saves the arrangement of panels, with options to capture Panel Locations, Keyboard Shortcuts and Menus; a Choose-a-workspace dropdown in the application bar; the last arrangement is kept automatically and the saved one can be restored (https://helpx.adobe.com/photoshop/desktop/get-started/learn-the-basics/save-custom-workspaces.html). Takeaway: a *reset* of a workspace to its saved form must exist.
- **Affinity (Photo/Designer 2).** Panels float alone or in groups; groups make a Studio; presets saved per persona (Window > Studio > Manage Studio Presets), "Reset Studio" restores the default (https://affinity.help/photo2/English.lproj/pages/Workspace/customizingWorkspace.html, via search snippet). Takeaway: presets belong to a mode, a reset is one command.
- **IntelliJ tool windows / Eclipse perspectives.** IntelliJ's page states only that tool windows attach to the bottom and sides, can be detached to separate windows and have a view-mode menu in their header (https://www.jetbrains.com/help/idea/tool-windows.html). Eclipse perspectives (views plus an editor area, resettable) could not be fetched. [U] for both beyond that. Not a model for Fugue: fixed zones.
- **ComfyUI's new frontend (GPL; docs only).** Left sidebar tabs (Assets, Nodes, Models, Workflows, Apps); a **right side panel that follows the canvas selection**: nothing selected shows "Workflow Overview" (Parameters, Nodes, Settings), one node shows its Parameters, Info, Settings (and Errors), several show the union; open or closed state is remembered between sessions, the content is not (https://docs.comfy.org/interface/right-side-panel.md). That is the Properties view's content rule, and it confirms that following selection is what people expect. ComfyUI has no free splitting [U: from the docs read, nothing describes it].

## 2.3 Qt options

- **Qt Quick `SplitView`** (https://doc.qt.io/qt-6/qml-qtquick-controls-splitview.html, verified). Attached `minimumWidth/Height`, `preferredWidth/Height`, `maximumWidth/Height`, `fillWidth/Height`; "a split item cannot be dragged to be smaller than its minimumWidth"; the last visible child fills by default; dragging a handle overwrites `preferredWidth`; do not set the item's own width or height; `saveState()` "saves the preferred sizes of split items into a byte array", `restoreState()` reads them back and returns a bool; handles are a visual `Component`; `resizing` is a read-only flag. No documented nesting, no drag of items between views, no drop zones. Limits for us: sizes in pixels (not proportional), the fill item takes all window growth (not proportional), the saved state is an opaque blob tied to child order, nothing in it can be version-checked. Fine for a fixed two-pane chrome; wrong as the persistent model of a free tree.
- **KDDockWidgets (GPL-2/3 or commercial; docs only).** Dual licensed (https://github.com/KDAB/KDDockWidgets); "supports QtWidgets and QtQuick/QML"; partial layout save and restore. Not usable: GPL conflicts with Fugue's licence unless bought [U: Fugue's licence was not re-checked here; LICENSE in the repo decides]. Useful as a feature reference only (floating windows, tab groups, saved layouts).
- **Qt Advanced Docking System (LGPL-2.1).** Widgets-based (`QMainWindow`, `CDockManager`), perspectives and saved state; the README mentions a `QQuickWidget` in its demo but documents no Qt Quick API (https://github.com/githubuser0xFFFF/Qt-Advanced-Docking-System). Fugue has no `QWidget` window; adopting it means a widgets host around a Quick scene. Rejected.
- **QML docking ports.** `huacnlee/qmldock`: no licence in the GitHub metadata, last push 2024-08, README says development phase; `hamedmasafi/qmldock` fork: no licence, last push 2025-07. Rejected: no licence means no reuse.
- **Qt Quick without widgets is feasible**: a split tree is ~150 lines of QML plus a C++ model. Resize handles are `DragHandler`s on thin items; nested recursion by a `Component` that instantiates itself or `Loader` for leaves; floating windows are `Window` items [U: not tried here]. The hard parts are not the splitter but state, focus and context (section 5).

# 3. Fugue today: what can become a view

Read: `src/Main.qml` (575 lines), `src/qml_app.h`, `src/canvas/FugueCanvas.qml` (1637), `canvas_model.h`, `LargeViewDialog.qml`, `MaskEditor.qml`, `CanvasHistoryDialog.qml`, `RunQueuePanel.qml`, `WorkflowsPanel.qml`, `src/panels/*`, `src/workflow/workflows.h`, `tab_session.h`, `src/commands/*`, `side_panels.h`, `chrome_visibility.h`; spec 12.10, 12.11; `tests/canvas/test_canvas_window.cpp`.

Naming trap: in the code and docs "canvas" is the *node graph* (`FugueCanvas`, `App.canvasModel`, `canvas_commands`), while #206 "Canvas" is the *image canvas* (store, revisions). The view types should be named **Graph** (today's `FugueCanvas`) and **Canvas** (the picture editor); the code names stay.

## 3.1 What is global (stays on `App`, never per area)

- **Project and root**: `App.projects`, the state folder (`tabs.json`, `chrome` file, side panel file); a project switch starts a new window (spec 12.10), so layouts can be per root.
- **Open workflows and the current document**: `App.workflows` (tabs, `current`), with one `CanvasModel` for the shown tab: `Workflows` swaps each tab's document and its `QUndoStack` into that single model (`takeUndoStack`/`setUndoStack`, `workflows.h`). **One model means one shown document per window.** Two Graph areas can show the same tab; they cannot show two tabs. That is acceptable for epic #217 (and it matches Blender: a window has one active scene); two documents side by side is a separate, larger change [open question].
- **Selection and scope**: `CanvasModel::selection`, the group `breadcrumb`/scope, `linkDrag`, `pointer`, the `gesture`: all model-level, not per view. Selection must stay shared (it is the source of the active target). `pointer`, `linkDrag` and the gesture need to be per Graph view or guarded so only the area under the pointer writes them.
- **Runs**: `App.runs` (`CanvasRuns`), `App.runQueue` (entries, history, `watching`), `App.runBar`; one engine, one queue per window. `RunQueue::watching` is a bool set by the panel's creation; with two Queue views it must be a counter.
- **Services**: `App.theme`, `App.commands`, `App.settings`, `App.mediaLibrary`, `App.imageActions`, chrome visibility.

## 3.2 What is chrome around the views (stays in `Main.qml`)

The menu bar (auto-hide), the workflow tabs strip, the helper notice, the side tab strip and `SidePanel` dock (node library, workflows panel), the Settings, Templates, Projects dialogs, `WorkflowDialogs` (file pickers, save questions), `CommandUi`, the chrome hint. In slice 0 the area container takes exactly the place `FugueCanvas` has in the `ColumnLayout` (with the side panel margins), so none of this moves.

## 3.4 Keyboard and focus today

- **Commands** are a registry (`CommandRegistry`): ids, keys, a `context` (app, canvas, group-selected, group, run, compare), and tickets turn contexts on and off (`setContextActive`; `canvas` is set once at startup in `main.cpp:125` and again in `canvas_commands.cpp:111`; group and compare follow the selection; `run` follows the run state). `CommandUi.qml` binds one window-level `Shortcut` per active key. Keys belong to the *window*, not to the item under the pointer.
- **Text fields** take bare letters and Shift-only keys, Backspace, Delete, Tab and Enter (`textFieldFocus`, `belongsToTextField`), toggled by focus.
- **Per-view keys** live in the view: `FugueCanvas` has `Keys.onPressed` for Escape and Space (pan) and `onShortcutOverride` for Escape; `LargeViewDialog` handles 0, 1, +, -, Enter and forwards others through `keyPressed`; `MaskEditor` adds B E X L R I H and `[` `]`. `Window.activeFocusItem` and `forceActiveFocus` are used (canvas `focus: true`).
- **Overlay keys** sleep while the run queue panel is focused (`yieldKeys`).

Blender routes keys by the area under the pointer (section 2.1). Fugue can keep its window-level registry if the *contexts* follow the active area: when a Mask view is active, `mask` is active and its handlers apply to that area's editor; when a Graph view is active, `canvas` is. This keeps rebinding, the `?` overlay and the keymap file working unchanged. Hover versus click focus is a policy choice: Blender hovers; Fugue has text fields in every panel and focus-based code throughout, so recommend **click or keyboard focus makes the area active** (outline in the accent colour), the wheel and pointer gestures act under the pointer, and Tab/F6 [U: key not chosen] cycles areas. Confidence: medium; a "hover to activate" option could be a later preference, as Blender exposes preferences for layout behaviour.

## 3.5 Undo scopes

- **Graph**: one `QUndoStack` per workflow tab inside the shown `CanvasModel`, whole-document snapshots, at most 50 steps (spec 12.11); viewport and selection are not edits.
- **Mask and Paint**: their own tile-based undo while the editor is open (>= 100 steps), then one graph step on OK (`setMaskPath`, `setPaintPath`).
- **Canvas (#206)**: revisions in the store with a head and candidates; History is the undo list, not a `QUndoStack` [spec 14.5, `canvas_history.h`].
- **Recommendation**: `Edit > Undo/Redo` and Ctrl+Z act on the active area's *undo scope*: the view reports `canUndo/undoText`. Graph and Properties share the graph stack. A Mask or Paint view keeps its own stack while edited and, on leaving (follow target changes, area closed, tab switched) or on an explicit Apply, commits **one** graph step; "Cancel" becomes "Revert". Blender in contrast keeps one global undo for data plus per-mode stacks [U: not verified in the pages read]. Conflict case: undoing a graph step while a Mask view holds a working copy of that node's mask: the view must be told (`target changed`) and drop or re-read its copy.

# 4. Performance, tests, persistence, a view shown twice

## 4.1 Two heavy views at once

- **What exists.** `test_canvas_window.cpp` opens 300 nodes and 600 wires and bounds CPU time and an exact **item count** (about 3870 items in the window on 2026-11-20); node faces are made lazily when they first come into view and a node off-screen is two items. The Graph view costs *items*; the Canvas view costs *texture memory and upload*. They add, not multiply: Qt Quick's scene graph renders every visible item of the window in one pass of one render loop.
- **Canvas picture size.** The canvas store caps are 8192 x 8192 (canvas-research.md section 2.1); one 8192 x 8192 RGBA texture is 256 MiB, 4096 x 4096 is 64 MiB. A Canvas view must show tiles or a downscaled level (the code already has 64 px paint tiles and tile hashes in `engine/paint_*`), never one full-size `Image`. This is a #216 constraint independent of workspaces, but two views that both want the GPU make it matter. [U] Measured cost of the two together was **not measured**: the first spike of slice 5 should put the 302-node scene and a 4096 x 4096 12-layer canvas in one window and read frame time with `spikes/canvas/render-timing.py` offscreen and on the GPU.
- **Hidden areas cost nothing if hidden properly.** A Loader with `active: false` or an item with `visible: false` is skipped by the scene graph; a maximized area should deactivate (not just cover) the others, with state kept in the tree. Blender maximize keeps the hidden areas' data (areas page).
- **Item budget (#5).** `Main.qml` makes panels and the toolbar "only when shown" and "not even a Loader is left standing" for them. The container adds a few items per area (frame, header, a Loader). With a hidden header in the single-area case, and the Graph declared statically, the default window's count must not move: assert it with the existing count in `test_canvas_window.cpp`.
- **Software renderer.** The dot grid uses a shader and `Loader` falls back without shaders ("the software renderer has no shaders", `FugueCanvas.qml`); the container must not add shader effects.

## 4.2 Offscreen testability

- The repo's windows are tested with `QQuickWindow` on the offscreen platform, grabbed with `test_support::grab()` (`tests/window_grab.h`: `grabToImage`, not `grabWindow`, because the rhi backend on offscreen reads garbage for later windows), `qmllint` on every file (`tests/qmllint.cmake`).
- **Split the layers.** (1) `AreaTree` is plain C++ (the same discipline as `chrome_visibility.h` and `tab_session.h`: "pure rules, no window"): split, join, swap, resize by ratio, clamp to minimums, serialize and deserialize, fallback; tests in `tests/panels/` with no window. (2) The QML `AreaNode` is tested with a tree JSON, an offscreen window of a given size, the sizes of leaf items checked against the layout, a grab compared by size not pixels, plus the item count. (3) Views are tested alone as today (`test_canvas_mask_editor.cpp`, `test_canvas_history_window.cpp`), not through the container, to keep targeted tests fast.
- Pointer drags of a handle are testable with `QTest::mouse*` on the offscreen window; **never** the real pointer, `ydotool` or host `hyprctl` (owner rule).

## 4.3 Persistence of a layout

- **Where.** `workspaces.json` in the root's state folder, next to `tabs.json`, `side panels` and the chrome file; per project. Not in the `.fugue` file: a layout is a view preference and workflow files are shared (the same reason tab colors are in `tab-colors.json`, spec appendix row on #98). Open question: a workflow hint like `layout.workspace: "inpaint"` that *suggests* a workspace on open [U, not designed].
- **Format.** Like `tabs.json` (`{"format": 1, ...}`, atomic write) and VS Code's serialized grid (section 2.2):
```
{"format": 1, "active": "w2",
 "workspaces": [{"id": "w1", "name": "Graph",
   "root": {"type": "leaf", "area": 1, "view": "graph", "state": {"graph": {...}}}},
  {"id": "w2", "name": "Inpaint",
   "root": {"type": "branch", "orientation": "horizontal", "children": [
      {"size": 0.62, "node": {"type": "leaf", "area": 2, "view": "graph", "state": {}}},
      {"size": 0.38, "node": {"type": "branch", "orientation": "vertical", "children": [...]}}]}}]}
```
  Sizes are proportions summing to 1, not pixels. A leaf keeps `state` as a map `viewType -> state` (Blender's `spacedata` list) so switching type does not lose the old state; `maximized` and `visible` flags as in VS Code.
- **Versioning.** `format` for the file; each view type has `stateVersion` in the registry and a `migrate(state)`; unknown keys are kept and written back (the `chrome_visibility` rule: "ids this version does not register are kept in the file untouched, so a newer or older build does not lose a choice").
- **Defaults and fallback.** The default workspace ("Graph": one Graph area) is built in and is not stored until the layout changes; no file means the default. A damaged file, an unknown `format`, a root that is not a branch or leaf, or numbers that do not validate: use the default, keep the bad file as `workspaces.json.bad`, and say so once in the window's notice line. An unknown view type becomes a placeholder area ("this view needs a newer Fugue", with a menu to pick another) and is preserved. A size below a view's minimum is clamped at layout time and never rewritten silently. "Reset workspace" restores the built-in preset (Photoshop's Reset Essentials, Affinity's Reset Studio, Blender's Defaults).
- **Save timing.** A short debounce after a change, as `tabs.json` does (a burst is one write), and at quit.
- **Never stored**: focus mode (as today, "a window always opens with its bars"), the active area's focus, selection.

## 4.4 A view shown twice

- **Graph twice, same tab**: works if the camera is per view (it is: `world.x/y/scale` live in the QML item) and the model stays shared. Costs: each Graph creates its own node delegates (items double; lazy creation keeps off-screen nodes cheap); `layout.view` is written from the last active Graph; `requestZoom/requestFit` signals and `pointer` must go to the active area only; keys go to the active area. Selection and scope (entered group) are shared, as Blender shares scene selection between viewports; per-area *scope* (two Graphs in different groups) is not possible with one model [open question, probably accept].
- **Mask/Paint twice on one node** and **Canvas twice on one canvas**: forbid by a `multiplicity` rule in the registry (`one-per-target`): the second view shows "being edited in area N" with a button to jump there. Viewer, Results, Queue, History, Properties: any number.
- **A target shared by two Viewers**: fine; each has its own zoom.
- Switching a type away from a Mask view that has uncommitted edits must ask or commit (same rule as leaving).

# 5. Architecture, slice 0, risks, order of slices

## 5.1 Parts

- **`AreaTree`** (C++, `src/workspace/area_tree.*`, QObject-free core plus a thin `AreaModel` for QML): nodes `Leaf{areaId, viewType, state map}` and `Branch{orientation, children[{ratio, node}]}`; operations `split(area, orientation, ratio)`, `join(a, b)`, `swap(a, b)`, `resize(branch, index, ratio)`, `setView(area, type)`, `maximize(area)`, `serialize/deserialize`, with minimum sizes asked from the registry. Alternating-orientation normalisation as in VS Code.
- **`ViewRegistry`** (C++ table like the side panels' table in `side_panels.cpp`: "a new panel is one row"): `{id, name (translated), glyph, component url, minWidth/minHeight, multiplicity (many | one-per-target), stateVersion, keyContexts, undoScope, follows (what target kinds it follows)}`.
- **`WorkspaceStore`** (C++): the list, the active workspace, load/save (`workspaces.json`), presets, reset; exposes `App.workspaces` (optional, null in a test window like `App.sidePanels`).
- **`ViewContext`** (one QObject per area, QML-visible): `areaId`, `viewType`, `state` (read/write map, persisted), `follow` ("target" | "pinned"), `pinnedTarget`, `target` (the effective target: the app's active target, or the pin), `active` (this area has focus), `requestOpen(type, targetParams)` (open-or-reuse, section 2.1 Temporary Editors). The data stays on `App`; this object is the only per-area thing.
- **`ActiveTarget`** (C++, owned by the app, derived from `CanvasModel::selection` and the node row data): `{node, kind (graph|paint|mask|image|compare|region|canvas|none), canvasId, region (rect), picture}`. Adding a kind is one row. It exists because "what a view follows" must not be re-derived by each view from the model.
- **QML**: `AreaNode.qml` (recursive: branch renders its children with handles, leaf renders `AreaFrame` = optional header with the type menu, a body `Loader`), `AreaHeader.qml` (type menu with the registry's glyphs, pin button, area menu: split, join, maximize, close, duplicate), `ViewFrame.qml` (extracted from `LargeViewDialog`).
- **Routing**: `ViewHost` keeps the active area and sets command contexts (`setContextActive`) and the undo scope when it changes.

## 5.2 Selection drives another view (the owner's two examples)

Rule (from Blender's Image Pin and Properties pin, and ComfyUI's panel): a view with `follow: "target"` always shows the app's `ActiveTarget`; a pinned view keeps its `pinnedTarget`. Whether a view *accepts* a target is its registry `follows` list.

- **Select a Paint node, the Mask editor view follows.** `ActiveTarget` becomes `{node: P, kind: "paint"}` (from `model.paintState(P).input` being set; `mask` for a mask input). A Mask view follows kinds `paint` and `mask`: it reads `paintState/maskState`, `App.runs.inputPicture(node)` and `inputFile` exactly as `openPaint/openMask` do today, and shows "Run the node above first" in place of the notice when the picture is missing. Selecting a non-paint node leaves the Mask view on its last target (it does not blank), as Blender's Image Editor keeps its image when the selection has none. Commit rule: switching target commits the working copy as one graph undo step (or asks, a setting; section 3.5).
- **Select a Canvas Region, the Canvas view shows its region.** `ActiveTarget` becomes `{node: R, kind: "region", canvasId, region: rect}`, read from the Region node's inputs (a `canvasState(node)` accessor next to `maskState/paintState` in `CanvasModel`, new, small). The Canvas view loads that canvas (following only the canvas, not the node) and draws the rectangle as an overlay; dragging the overlay writes the Region node's inputs through the same model call a widget uses (one undo step). Selecting a `fugue/canvas` node alone shows the canvas without a region. History follows `canvasId` the same way.
- **Selection from the other direction**: a view may *request* a selection (click a result row, choose a revision): `ViewContext.requestSelect(node)` goes through `CanvasModel`, so every other area sees it. Views never keep a private "current node".
- **Loops**: a view must not change the target in response to the target changing (Blender has the same hazard with pins); the rule is views write only on user input.
- Why a target object and not each view reading `model.selection`: three views would each reimplement "the first selected node of kind X", the Graph's group scope, and the pin.

## 5.3 Slice 0: one area, nothing visible changes

- Add `src/workspace/` with `AreaTree` (leaf-only in use), `ViewRegistry` (one row: `graph`), `WorkspaceStore` with the built-in default and no file, `App.workspaces` (optional, null in test windows).
- `Main.qml`: `AreaNode` replaces `FugueCanvas` in the `ColumnLayout` with the **same item** underneath: `objectName: "canvas"`, same `Layout.*`, same margins, all tests and the screenshot tests keep finding it. For the single default leaf the Graph is declared statically (no `Loader`), the header is hidden when there is one area (shown from slice 1 by the View menu, or as soon as the tree has a split), so the item count in `test_canvas_window.cpp` does not move.
- Everything on the Graph that reaches outside (`runToolbarItem`, `runQueueItem` parented to `fugueCanvas`, `NodeSearchPopup { canvas: fugueCanvas }`, `WorkflowDialogs { canvasView: fugueCanvas }`, the library drop mapping) keeps its reference: no Graph change in slice 0.
- No layout file is written until a layout change exists (nothing in slice 0 changes it). `tabs.json` and the chrome file stay as they are.
- Tests: the `AreaTree` unit tests (serialize round trip, fallback, clamp); the existing window tests unchanged and green; one new test that the default workspace yields one leaf of type `graph` and the same item count.
- Spec and `docs/ui-ergonomics.md` entries (the repo rule for any window UI change) arrive with slice 1, where the header and handles are real controls.

## 5.5 Risks

1. **One `CanvasModel`**: a second Graph on another tab is impossible; two Graphs on one tab share scope and selection. Accept and say so; the fix (a per-view model facade) is large.
2. **Model-level pointer, linkDrag, gesture, zoom signals** assume one Graph. Medium effort, mechanical, must be done in slice 1 or 2 before a second Graph is allowed (until then, forbid a second Graph in the type menu).
3. **Modal to view for Mask/Paint**: commit and cancel semantics, undo interplay, the "run the node above first" case, Escape/Enter keys. The riskiest slice for correctness; keep the dialogs as wrappers until it is proven.
4. **Item budget and startup time**: every area adds frame items; the default window must not grow (assert in test). A hidden area must really deactivate.
5. **Key contexts**: window-level `Shortcut`s with contexts switched by the active area: a stale context after an area closes or changes type would leave keys bound to nothing or to the wrong view. Needs one place (`ViewHost`) and tests for each transition.
6. **Floating items parented to the Graph** (run toolbar, queue, search, context menu, dialogs): in a smaller Graph area they must stay inside the area and not under neighbours; the Queue view makes the floating queue panel redundant, so decide whether the run bar's queue button toggles an overlay or opens a Queue view.
7. **Layout versus tabs versus workspaces**: Blender has no document tabs; Fugue has two tab-like things (workflow tabs, workspace tabs). Two strips are confusing; recommend the workspace switcher sits in the menu bar row or under the type menu and shows only from the second workspace (as the workflow tabs appear from the second workflow).
8. **Small windows**: `minimumWidth: 640` and side panels leave little room; the default window must stay a single area, and splitting must refuse below each view's minimum (VS Code rule: a branch's minimum is the largest child minimum).
9. **Translations and right-to-left**: the window mirrors for RTL (`LayoutMirroring`); split orientation, handles and saved ratios must be logical (start/end), not left/right.
10. **Memory**: two big pictures (Canvas and Mask editor on a large paint) at once; see 4.1.
11. **Licence hygiene**: nothing was copied; only GPL docs were read for Blender, Krita, KDDockWidgets, ComfyUI. VS Code (MIT) may be read, but a TypeScript grid does not port; only the data shape is reused.
